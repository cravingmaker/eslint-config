An audit of the result led to twelve more steps, which ran from 8 to 13 October 2026 and are complete as well: see [Audit follow-up](#audit-follow-up).

## Decisions

| Topic                        | Decision                                                                                                                           |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Source layout                | One tree, `src/configs/`. A feature is one file and becomes a folder only when it outgrows one                                     |
| Public API                   | `createConfig(options, ...userConfigs)` and its types. Feature builders stay internal                                              |
| Old option names             | Clean break, no compatibility adapter. The README has the migration notes                                                          |
| `environments` and `globals` | Kept as in 0.1.0, applied to every JavaScript, TypeScript, and Svelte block                                                        |
| `plugins`                    | Removed. Extra plugins go in `userConfigs`, where they can be scoped with `files`                                                  |
| CommonJS                     | Not supported. `.cjs` and `.cts` files get no rules                                                                                |
| Composition                  | `Promise<Linter.Config[]>` built from native flat configs, without a composer class                                                |
| Rule overlap between plugins | Explicit ownership in rule maps: winners are enabled and alternatives stay off with `Handled by` comments                          |
| New upstream rules           | The effective-policy snapshots are the review gate. Every current rule is classified explicitly; new upstream rules require review |
| File-role exceptions         | A dedicated module, `configs/exceptions.ts`, added to only with evidence                                                           |
| A feature's `files`          | Narrows the feature's default files and cannot add a file type, which takes a user config that copies a block                      |
| Rule option typing           | Generated with `eslint-typegen` into `src/typegen.d.ts`, which is not committed                                                    |
| Formatting                   | Prettier runs separately. Layout rules are off in the rule maps, and `tests/policy/formatter.test.ts` guards them                  |
| Scope anchoring              | No `basePath`. `projectRootDirectory` decides the manifest, the tsconfig directory, and the import resolver                        |
| TypeScript first             | Typed linting is on by default, with typescript-eslint's strict rules. `typescript.typeChecked: false` turns it off                |
| Compiler options             | The README asks for `strict`, `noImplicitReturns`, and `allowUnreachableCode: false`, and the compiler owns those checks           |

## Documented limits

Step 11 of the [audit follow-up](#audit-follow-up) reproduced these on `b4c947f`, and step 12 again on `fd1121d`, with no change to the configuration or its default policy:

- **TypeScript compatibility.** The installed typescript-eslint 8.70.0 declares `>=4.8.4 <6.1.0` in `peerDependencies.typescript`. A consumer without TypeScript gets 6.0.3 automatically. With TypeScript 7.0.2 installed, npm succeeds with `ERESOLVE overriding peer dependency`, but ESLint exits with code 2 while loading the config: `TypeError: Cannot read properties of undefined (reading 'Intrinsic')` from ts-api-utils. The README's requirements state the supported range and exclude TypeScript 7.
- **Workspace path aliases.** The import resolver starts at `tsconfigRootDir` and follows the root tsconfig's `references`; it does not discover workspace tsconfigs as typed linting does. An alias defined only in a workspace's `compilerOptions.paths` is reported by `import-x/no-unresolved`. Referencing that workspace from the root, or adding a user config for its files with `import-x/resolver-next` pointed at its tsconfig, resolves the alias. The README's "Monorepos" section describes both.
- **JSX extensions.** `.js` files with JSX fail with `Parsing error: Unexpected token <`, even with React on. `.mtsx` is in the TypeScript and React globs, but `<div />` fails with `Parsing error: '>' expected.`. `.jsx`, `.mjsx`, and `.tsx` parse the same source. The README's "Limits" section names these extensions.

Step 11's comment cleanup is skipped: step 9 already moved `no-nested-ternary` out from under "Off while unicorn is on" and gave it its own explanation in #90.

## Open questions

Each of these needs a decision. They come in three groups: one question with two directions, what the rewrite found and did not change, and what the audit follow-up found and did not change.

The README lists those of the first two groups that affect users as known issues. Both groups were reproduced against the release candidate on 7 October 2026, and again on `fd1121d` on 13 October 2026, when the audit follow-up closed. The follow-up settled one of them: "`files` without an extension" became the decision "A feature's `files`" in step 10. The others stand as they were.

### TypeScript files that the TypeScript feature leaves out

The JavaScript and code-quality blocks match TypeScript files through `sourceFiles`, but only `typescript/parser` gives them a parser that reads TypeScript. A TypeScript file that the feature leaves out, with `typescript: false`, outside `typescript.files`, or in `typescript.ignores`, is therefore linted with espree and fails with `Parsing error: Unexpected token :` at its first type annotation. Two directions:

- **Leave those files unlinted,** as every other language feature does: the shared blocks reach TypeScript files only where the TypeScript feature does. Every shared feature's default files would then depend on the `typescript` options, and `typescript.ignores` would reach the other blocks as negated patterns in AND arrays, such as `[["**/*.ts", "!**/*.generated.ts"]]`, which ESLint 10.11 supports. The type-aware scope stays narrowed to `typescript.files` without `typescript.ignores`, as it is now.
- **Keep them parseable:** `typescript/parser`, and the core rules that the compiler checks, cover every TypeScript file that a shared block lints, and `files` and `ignores` narrow only the TypeScript rules. Core rules that typescript-eslint replaces would then run on TypeScript code without their replacements, and `typescript: false` would still need the first direction. `resolveTypeAwareScope` would narrow to that wider scope, so the type-aware rules of `functional` and `node` would reach those files again, with type information.

The audit follow-up did not settle this, and changed two things around it. Since step 2, `withoutIgnores` builds the type-aware scope out of the negated patterns that the first direction needs. Since step 10, a directory is enough as `typescript.files`, which makes the problem easier to meet: with `typescript: { files: ["packages/api/**"] }`, the TypeScript files of every other directory fail to parse.

### Found, not changed

- **Typed linting reports every React component.** `@typescript-eslint/naming-convention` allows only camelCase for functions and variables, so a component in a `.tsx` file is reported. `functional/no-return-void` reports event handlers and effects that call a state setter, and `functional/functional-parameters` reports a handler written inline in JSX, because its `ignoreLambdaExpression` exempts only call arguments. Without React's types, which React does not ship, every value from React is an error type besides. The React fixtures are therefore linted without type information. Since typed linting became the default on 19 October 2026, a React project with TypeScript files meets this without setting any option.
- **No manifest without peer dependencies passes.** `package-json/require-peerDependenciesMeta` requires the field, and `package-json/no-empty-fields` reports it when it is empty, so only a package with peer dependencies can have a clean `package.json`. `require-author`, `require-devDependencies`, `require-devEngines`, and `require-scripts` apply to private packages as well. JSON has no disable comments, so an application's manifest cannot pass.
- **A bracketed URL stops the run.** In a Markdown file, a URL or email address in square brackets, such as `[https://example.com]`, makes five rules of `@eslint/markdown` 8.0.3 throw "Custom getLoc() method must be implemented in the subclass": `no-bare-urls`, `no-invalid-label-refs`, `no-missing-label-refs`, `no-reference-like-urls`, and `no-space-in-emphasis`. ESLint stops for every file. The choices are an upstream fix or turning the five rules off.
- **Self-closing custom elements.** `@html-eslint/require-closing-tags` has `selfClosing: "always"` and `selfClosingCustomPatterns: ["-"]`, so in an HTML file it fixes `<my-element></my-element>` to `<my-element />`. HTML ignores that slash on elements that are not void, so a browser nests the content that follows inside the custom element. `selfClosingCustomPatterns: []` keeps explicit end tags. Prettier keeps either form.
- **`.svelte.mjs` and `.svelte.mts`.** `svelteFiles` includes them, but svelte-eslint-parser treats only `.svelte.js` and `.svelte.ts` files as rune modules. It reads the other two as components and fails with `Parsing error: Expected token }`. Leaving them out of `svelteFiles` would make them plain JavaScript and TypeScript sources.
- **Legacy Svelte types.** Legacy TypeScript components type their props, events, and slots with the interfaces `$$Props`, `$$Events`, and `$$Slots`. `unicorn/name-replacements` asks for `$$Properties`, which Svelte's tooling does not read, and `unused-imports/no-unused-vars` reports `$$Events` and `$$Slots`, which no code references. `import-x/no-duplicates` reports `svelte/animate` and `svelte/transition` imported in one file, because the TypeScript resolver maps both to `svelte/types/index.d.ts`.
- **Global declaration files.** A declaration file without imports or exports, such as the `vite-env.d.ts` that Vite generates, is reported by `import-x/unambiguous`, and its `/// <reference types="vite/client" />` by `@typescript-eslint/triple-slash-reference`. The module form, `declare global` with `export {}`, passes.
- **A blank line inside a doc comment.** `perfectionist/sort-modules` counts the blank lines inside the documentation comment of a member as spacing between it and the member before it in the same group, and reports "Extra spacing". Its fix leaves the comment alone, so ESLint reports circular fixes and the problem stays. `unicorn/no-asterisk-prefix-in-documentation-comments` makes every paragraph break in a doc comment an empty line.
- **A type-aware rule outside the type-aware blocks.** `unicorn/no-non-function-verb-prefix` declares that it needs type information and is on in every source, because the explicit Unicorn policy keeps it on. It does nothing in a file without type information, so it is harmless, and `tests/policy/type-information.test.ts` lists it as an exception. Moving it to a unicorn type-aware block would change the snapshots.
- **Express rules.** The explicit policy enables nine of the 28 rules in eslint-plugin-express-security 3.2.4 and disables the other 19. Supported peer versions start at 1.2.0; each receives the declared rules and option fields it supports.

### Found by the audit follow-up, not changed

The steps reported these in their pull requests and left them, because no step covers them. Each was reproduced on `fd1121d`. The README does not list them as known issues. One more is gone: `json.overrides` reached a JSON5 file that `json.files` named, as #81 reported, until step 10 made `files` narrow each JSON language.

- **`n/no-sync` stops ESLint in a JavaScript rune module.** With the default options in a project that declares `svelte`, a `.svelte.js` module that calls a function whose name ends in `Sync` inside a function, such as `flushSync()` from `svelte`, stops the run with "You have used a rule which requires type information". svelte-eslint-parser hands the module to typescript-eslint's parser, and the rule asks such a parser for type information. `node/rules-typescript` turns the rule off by the patterns of TypeScript files and Svelte components, which do not match `.svelte.js`. In a `.svelte.ts` module the rule is off, and in a plain `.js` file it reports the call. Found in #78.
- **A rule that needs type information in the overrides of another feature.** Since step 3, a feature keeps an override that turns such a rule on out of the files without type information, but only for the rules of its own plugin. `functional/prefer-immutable-types` in `typescript.overrides`, or `n/no-sync` in `security.overrides`, still stops ESLint in a TypeScript file without typed linting. The README says to override a rule in the feature that holds it. Found in #79.
- **Three more names of JSON files with comments.** `jsconfig.json`, a `.devcontainer.json` in the project root, and `.devcontainer/<folder>/devcontainer.json` are linted as JSON, where a comment is `Parsing error: Unexpected character '/' found.` The JSONC block matches `**/*.jsonc`, `**/tsconfig*.json`, `**/.vscode/*.json`, and `**/.devcontainer/*.json`. Found in #81.
- **The values of the options are not checked.** Step 6 checks the keys. A value of the wrong type passes in silence: `javascript: false` keeps the core rules on, `typescript: "strict"` and `typescript: { typeChecked: "yes" }` give the config of `typescript: true`, `react: "vite"` gives that of `react: true`, and `createConfig("strict")` that of a call without options. An unknown name in `environments` rejects with `TypeError: Cannot convert undefined or null to object`. With `// @ts-check`, the compiler reports each of them. Found in #82.
- **An override that is only a severity drops the options of the policy.** In a feature's `overrides`, an entry replaces the whole entry of the rule. `unicorn: { overrides: { "unicorn/template-indent": "warn" } }` therefore brings back the rule's own options, which check the `gql` and `html` templates that Prettier formats, and `"error"` for `react-refresh/only-export-components` drops the `allowConstantExport` of the Vite variant. In a user config, the same entry keeps the options of the policy, because ESLint merges it with the blocks before it. `CONTRIBUTING.md` says this to contributors, and "Feature values" in the README does not say it to users. Found in #89.
- **A package behind a symbolic link.** With the defaults, `n/no-unpublished-import` reports every relative import of a package that is not private when ESLint reaches its directory through a symbolic link: `"./local.js" is not published.` By its real path, the same package has no message. The temporary directory of macOS is such a link, so a test that lints a project there creates it by its real path. Found in #90.
- **An option that applies nowhere gives no message.** Each of these is accepted and does nothing: an override that turns on a rule that needs type information while `typeChecked` is off, `filesTypeAware` and `overridesTypeAware` while `typeChecked` is off, an override of a `react-refresh/*` rule while React Refresh is off, and a pattern of a feature's `files` that matches none of its default files. The README describes each case, and nothing reports one when ESLint runs. Found in #79, #80, #89, and #91. The plan lists the second under "Not planned".
- **A negated pattern in `svelte.ignores`.** `resolveSvelteComponents` leaves such patterns out of the components that the other features lint. With `svelte: { ignores: ["src/legacy/**", "!src/legacy/Keep.svelte"] }`, `Keep.svelte` gets the Svelte rules and no rule for its script. Since step 2, `withoutIgnores` could express the pattern. Found in #78. Resolved in [audit implementation Stage 10](../../AUDIT_RESULT_FOLLOW_UP_IMPLEMENTATION.md#stage-10-production-utilities-builders-and-svelte-ignore-negations): ordered negations now restore script rules and component exceptions within the caller's file scopes, and later positive patterns can exclude them again.

## Core policy follow-up — 17 October 2026

The maintainer's revised core rule maps are the policy reference. Dynamic
overlap/fallback blocks were removed in favor of explicit disabled alternatives
in their owning maps. Turning a winning feature off no longer revives another
rule. Disabled rules no longer need explicit option defaults. Tests, fixtures,
snapshots, and repository code follow the revised core policy.

## TypeScript first — 19 October 2026

The config became TypeScript first. `typescript.typeChecked` defaults to `true`, so
TypeScript files get the rules that need type information unless a project turns typed linting
off. Apart from `no-useless-return`, below, the policy did not change: with typed linting on,
the effective rules of each TypeScript file are those that `typeChecked: true` gave before. The
effective-policy snapshots record the default with type information, and an `untyped` scenario
replaces the `type-checked` one.

The README now names the tsconfig that the policy expects. TypeScript 6 turns `strict` on by
default, but earlier versions do not, so the README asks for it explicitly, with
`noImplicitReturns` and `allowUnreachableCode: false`, which the rule maps already relied on for
`@typescript-eslint/consistent-return`, `sonarjs/no-inconsistent-returns`, and
`no-unreachable`. This repository's tsconfigs set the same options. `noImplicitReturns` requires
a `return;` that `no-useless-return` removes, so the maintainer turned `no-useless-return` off in
TypeScript files and Svelte components, where the compiler owns return statements.
