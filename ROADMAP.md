# Roadmap

Work planned after 0.2.0. Each item says why it is open and what closes it. The items were reviewed on 24 October 2026 against `main` at `e2cb99a`.

## Temporary workarounds

These keep lint runs deterministic while an upstream rule is broken. A new version number alone is not evidence of a fix. Restore a rule only after the installed dependency combination passes the checks listed, and change its source comment, README entry, and tests in the same pull request.

- **Five Markdown rules.** `markdown/no-bare-urls`, `markdown/no-invalid-label-refs`, `markdown/no-missing-label-refs`, `markdown/no-reference-like-urls`, and `markdown/no-space-in-emphasis` are off: GFM autolink nodes without source positions make them throw in @eslint/markdown 8.0.3, which stops ESLint ([eslint/markdown#619](https://github.com/eslint/markdown/issues/619), open). Restore each rule when a corrected release lints every trigger in the Markdown tests, such as `[https://example.com]`, a bracketed email address, and `<www.example.com>`, and the rule's own reports and fixes come back, with GFM, front matter, math, feature scopes, and overrides unchanged.
- **Module spacing in Perfectionist.** `perfectionist/sort-modules` has `newlinesBetween: "ignore"`, because its fixer counts the empty line of a paragraph break in a documentation comment as spacing between two members, reports "Extra spacing", and fixes nothing, so `eslint --fix` loops. No upstream issue exists: report it with a documentation comment that has a paragraph break, above a function that follows another function. Restore the spacing when a corrected release passes the function-declaration and mixed samples of `tests/policy/fix-convergence.test.ts`, with and without leading asterisks, through repeated ESLint and Prettier runs. Perfectionist 5.13.0, released on 20 October 2026, is not checked yet.
- **Padding in Svelte scripts.** `@stylistic/padding-line-between-statements` skips statements whose parent is a Svelte script element, so the internal `@cravingmaker/svelte-function-variable-padding` rule adds the blank line after a function-valued variable at the top level of a Svelte script. No upstream issue exists: report it. When Stylistic supports those statements, remove the internal rule, and tell consumers who override its ID in the release notes.
- **`@typescript-eslint/prefer-regexp-exec`.** The rule is off in the typed and untyped maps, because its fix turns `text.match(new RegExp(source))` into `new RegExp(source).exec(text)`, which returns one match where `source` has the `g` flag. Upstream closed [typescript-eslint#12827](https://github.com/typescript-eslint/typescript-eslint/issues/12827) as not planned on 16 September 2026, so a corrected rule is not expected. Decide whether the rule stays off for good; if it does, the README and the source comments stop calling it temporary. `regexp/prefer-regexp-exec` still reports `.match()` calls for manual review.

## Upstream dependencies

- **Vulnerable dependencies of consumers.** `npm audit` in a project that installs this package reports `deepmerge-ts` below 8.0.0 through `eslint-plugin-functional` 10.0.1 ([GHSA-ggr8-5vv4-36mx](https://github.com/advisories/GHSA-ggr8-5vv4-36mx), high), and `katex` below 0.18.2 through `micromark-extension-math` 3.1.0 and `@eslint/markdown` 8.0.3 ([GHSA-238p-pmpm-9mq7](https://github.com/advisories/GHSA-238p-pmpm-9mq7), low). Both are the latest releases. This repository forces the patched versions with `overrides`, which npm applies only in the root project, so its own audit is clean. Ask the two projects to move to `deepmerge-ts` 8 and `katex` 0.18.2 or later. When both release, update the dependencies, then remove the `overrides` from `package.json` and the known issue from the README.
- **TypeScript 7.** typescript-eslint 8.72.0 still declares `typescript: >=4.8.4 <6.1.0`, while TypeScript 7 is the `latest` version on npm. When typescript-eslint supports it, upgrade, update "Requirements" in the README, which describes the error that TypeScript 7 gives today, and lint the typed fixtures with it. Consider a `typescript` peer dependency with the range of typescript-eslint, so that `npm install` fails instead of ESLint; it needs a tested lower bound for the `minimum-peers` job of CI.
- **`n/no-unpublished-import` through a symbolic link.** With the defaults, the rule reports every relative import of a package that is not private when ESLint reaches the package through a symbolic link: `"./local.js" is not published.` By its real path, the same package has no message. Report it to eslint-plugin-n with a reproduction.

## Known issues to resolve

The README lists these under "Known issues" and "Limits". Each one needs a policy decision first.

- **TypeScript files that the TypeScript feature leaves out.** The JavaScript and code-quality features lint them, but only `typescript/parser` reads TypeScript, so they fail with `Parsing error: Unexpected token :`. Since `files` narrows, `typescript: { files: ["packages/api/**"] }` is enough for every other TypeScript file to fail. Two directions:
  - Leave such files unlinted, as every other language feature does. The shared features' default files then depend on the `typescript` options, and `typescript.ignores` reaches their blocks as negated patterns in AND arrays.
  - Keep them parseable: `typescript/parser` and the core rules that the compiler checks cover every TypeScript file that a shared feature lints, and `files` and `ignores` narrow only the typescript-eslint rules. Core rules that typescript-eslint replaces then run in those files without their replacements, and `typescript: false` still needs the first direction.
- **React handlers and effects with typed linting.** `functional/no-return-void` reports event handlers and effects that call a state setter, and `functional/functional-parameters` reports a handler written inline in JSX, because its `ignoreLambdaExpression` exempts only call arguments. Today the way out is `ignoresTypeAware` for React files, which gives up their typed checks.
- **Application manifests.** `package-json/require-author`, `require-devDependencies`, `require-devEngines`, and `require-scripts` apply to private packages as well, and JSON has no disable comments, so an application needs `packageJson.overrides`.
- **Legacy Svelte types.** `unicorn/name-replacements` asks to rename the `$$Props` interface, which Svelte's tooling reads by that name; `unused-imports/no-unused-vars` reports `$$Events` and `$$Slots`; and `import-x/no-duplicates` reports `svelte/animate` and `svelte/transition` in one file, because both resolve to one declaration file.
- **Global declaration files.** `import-x/unambiguous` reports a declaration file without imports or exports, such as the `vite-env.d.ts` that Vite generates, and `@typescript-eslint/triple-slash-reference` its `/// <reference types="vite/client" />`.
- **JSX file extensions.** A `.js` file with JSX fails to parse, even with `react: true`, although a JavaScript Next.js project names its pages so. `.mtsx` is in the TypeScript and React globs, but typescript-eslint parses JSX in `.tsx` files only. Decide whether `.js` files get JSX while React is on, and whether `.mtsx` stays in the globs.

## Options and overrides

- **Option values are not checked.** `createConfig()` rejects unknown keys, but a value of the wrong type passes in silence: `javascript: false` keeps the core rules on, `typescript: "strict"` and `typescript: { typeChecked: "yes" }` give the config of `typescript: true`, and `createConfig("strict")` that of a call without options. An unknown name in `environments`, such as `"nodejs"`, rejects with `TypeError: Cannot convert undefined or null to object`. With `// @ts-check`, the compiler reports each of them.
- **Options that apply nowhere give no message.** `filesTypeAware` and `overridesTypeAware` while `typeChecked` is `false`, an override of a `react-refresh/*` rule while React Refresh is off, and a feature's `files` pattern that matches none of its default files are accepted and do nothing. The README describes each case.
- **A rule that needs type information in another feature's `overrides`.** Each feature keeps an override that turns on one of its own type-aware rules out of the files without type information, but not an override of another plugin's rule. With typed linting off, `typescript: { overrides: { "functional/prefer-immutable-types": "error" } }` or `security: { overrides: { "n/no-sync": "error" } }` stops ESLint in a TypeScript file with "You have used a rule which requires type information". The README asks for each rule to be overridden in its own feature, and `javascript: { overrides: { "unicorn/no-null": "off" } }` changes nothing; rejecting another feature's rule IDs would turn both mistakes into clear errors.
